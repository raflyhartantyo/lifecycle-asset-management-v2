=== Master tables ===

Master_Asset (12).csv
- Function: Asset register, the core table. Each row is one asset.
- Rows: about 2,180
- Columns:
  - Asset_ID - unique asset key, format ASSET/{Function_ID}/{Asset_Type_ID}/{sequence}
  - Modified - last modified timestamp
  - Organization_ID - owning organization (links to Master_Organization)
  - Accounting_Asset_Code - accounting asset code (e.g. KO-000127/99/10, Y2004070-402549)
  - Asset_Name - asset description
  - MYID_Asset_Owner - MYID of the employee who holds the asset (links to Master_Employee)
  - MYID_Business_Owner - MYID of the business owner
  - Asset_Condition - physical condition (Good, Broken)
  - Asset_Status - status (In Use, Available, Auction, etc.)
  - Location_ID - location (links to Master_Location)
  - Asset_Type_ID - asset type (links to Master_Asset_Type)
  - Category_ID - category (links to Master_Category)
  - Environment - deployment environment (e.g. Not Applicable)
  - Merk - brand
  - Sub_Merk - sub-brand or model
  - Lifespan - useful life in years (inferred)
  - Arrival_Date - date the asset was received
  - Purchasing_Price - purchase price (IDR)
  - Function_ID - function that owns the asset (links to Master_Function)
  - Updated_Date - date of last update
  - Update_Type - type of last update (e.g. Initialization, Stock Opname, Mutation)
  - Supplier - supplier name
  - Remarks - free-text notes
  - Book_Value - current book value
  - HostName - computer host name
  - Serial_Number - manufacturer serial number
  - EndOfSupport - vendor end-of-support date
  - EndOfLife - end-of-life date
  - LicenseEndDate - software license expiry date
  - ID - record sequence number (inferred)
  - SODate - date of last stock opname
  - SO_Method - how the last stock opname was done (e.g. Manual)
  - ID Number - asset number label (inferred)
  - Asset_Sub_Status - sub-status (In Use, etc.)

3. Table relationships

Theory: Master_Asset is the hub. Each asset points to its type, category, function, organization, location, and two employees. The history tables link to assets by Asset_ID.

Primary keys (verified unique)
- Master_Asset - Asset_ID (also Accounting_Asset_Code) - 2,179 rows
- Master_Employee - MyID - 2,677 rows
- Master_Asset_Type - Asset_Type_ID - 26 rows
- Master_Category - Category_ID (lookup)
- Master_Function - Function_ID (lookup)
- Master_Organization - Organization_ID (lookup)
- Master_Location - Location_ID (lookup)

Foreign keys from Master_Asset (verified, 0 orphans)
- Asset_Type_ID -> Master_Asset_Type
- Category_ID -> Master_Category
- Function_ID -> Master_Function
- Organization_ID -> Master_Organization
- Location_ID -> Master_Location
- MYID_Asset_Owner, MYID_Business_Owner -> Master_Employee.MyID

Lookup chain (verified, 0 orphans)
- Master_Asset_Type.Category_ID -> Master_Category
- Master_Asset_Type.Function_ID -> Master_Function
- Master_Function.Organization_ID -> Master_Organization

Tables that reference Master_Asset
- Asset_Movement_History.Asset_ID -> Master_Asset.Asset_ID: 45 IDs not in Master_Asset (see known issues)
- Inactive Assets.Asset_ID -> Master_Asset.Asset_ID: 2 of 2 not in Master_Asset (expected for disposed assets)
- Inactive Assets.Asset_Type_ID -> Master_Asset_Type: 0 orphans
- AuditLog (TargetList = Master_Asset).ItemId -> Master_Asset.Asset_ID: 129 of 739 use a numeric ID instead of the ASSET/... key

Other links
- Acces_Matrix.Title -> Master_Employee.MyID (0 orphans). Screens use this for role checks.
- Master_Inventories.Category -> Master_Asset_Type (0 orphans)
- Master_Asset.Accounting_Asset_Code is the key screens use for asset matching.
- Screens use *_Cache collections (Master_Asset_Type_Cache, Master_Employee_Cache, Master_Location_Cache, Master_Category_Cache) as local copies keyed on the same IDs.

Screen join keys
- Role check: Acces_Matrix.Title = LookUp(Master_Employee, Email = User().Email).MyID
- Asset matching: Master_Asset.Accounting_Asset_Code
- Stock opname and reconciliation requests are matched by GUID or Title (for example Temp_Acc_Reconcile.Title = Job_ID).

Known issues
- Asset_Movement_History: 45 Asset_IDs are not in Master_Asset. 2 are in Inactive Assets (disposed). 43 are unexplained: their last recorded status is mostly Available (24) or In Use (19), so they do not look disposed. Check these before treating them as deleted. One ID (17020260902110956956) has a non-standard format and is probably a legacy or bad entry.
- Inactive Assets: ASSET/FNC-01/ATP-013/4695 also appears in Asset_Movement_History, so the disposal table and the movement log overlap.
- AuditLog: 129 of 739 Master_Asset entries use a numeric ItemId. Deferred: to be changed in the future.
- Inventories_Movement_History: 4 Title GUIDs are not in Master_Inventories. These are placeholders, not data errors.
- Temp_* tables store progress and history as JSON fields, because the full process is too large for one table. Joins happen by parsing that JSON in the screens. This is by design.
- Inventories_Movement_History: no screen writes it yet. It should be written by inventory registration and inventory movement. Incomplete, to be completed in the next iteration.

Notes for the handover
1. Caches are deliberate. Master_Asset_Type_Cache, Master_Category_Cache, Master_Employee_Cache, and Master_Location_Cache hold local copies of the master tables. Searches use the caches instead of calling the SharePoint connector each time. This makes the app lighter and works around the Power Apps limit of 2,000 items per SharePoint connector call. Changes to the source list show in the cache only after it is refreshed.
2. Inactive Assets is written through a form. ALM - Dispose declares Inactive Assets as a form data source. The table is written when the form saves, not by an explicit Patch on the table name. Check this before relying on it.
3. Temp tables are JSON. Temp_Stock_Opname, Temp_Acc_Reconcile, and Stock_Opname_InUse hold progress in JSON fields. The table-level map does not show the field-level dependencies.
4. Inventories_Movement_History is incomplete. It should be written by inventory registration and inventory movement, but no screen writes it yet. The next iteration should complete this.
5. Acces_Matrix is read by almost every screen as the role check. Changing a role there changes access across the app.

6. Access control

How access is decided (current design)

1) Identity. Each screen resolves the signed-in user with LookUp(Master_Employee, Email = User().Email).MyID. Planned change: use the Microsoft 365 user connector instead (see Future direction).

2) Permission flags. Acces_Matrix has one row per user, with True/False flags. Screens check them with LookUp(Acces_Matrix, Title = <MyID>, <Flag>).
- Transaction - can open transaction screens
- Master_Data - can view master data
- Master_Data_Edit - can edit master data (the ALM - XXX editors)
- Reconciliation - can run accounting reconciliation
- Asset_Management - can manage assets
- Inventories_Management - can manage inventory
- SO_Requester - can start a stock opname
- SO_Respondents - can approve or confirm a stock opname
- Disposal Request - retired with the disposal module. Not used.

3) Stock opname roles
- Requester (SO_Requester = True): starts the opname. The Start SO button is enabled only for requesters. Requesters see all rows on the request list.
- Respondent (SO_Respondents = True, plus a matching row in the request's approver list): confirms assets and saves responses. The approver row holds the respondent's Role and Access values.

4) Asset scope for respondents. Once a respondent opens a request, the asset list is filtered by the approver's Access value (current, hardcoded):
- all or All (see known issues) - every asset type
- Data Center - ATP-020, ATP-012, ATP-019, ATP-004, ATP-025, ATP-005, ATP-017
- Service Management - ATP-013, ATP-010, ATP-016, ATP-003, ATP-018
Planned change: the group comes from the asset's function, looked up through Master_Asset_Type and Master_Function, instead of a hardcoded ID list.

12. Improvement priorities and redesign direction

This is a total redesign, not an incremental fix. The current app is the reference for business rules and data only, not for layout or structure. Priorities, in order: simple, consistent (teratur), Zurich-styled, and scalable to the two other Zurich entities.

Notable improvements
- Scalability to different entities: one shared set of lists with an Entity column on every table. Screens filter by the selected entity. ORG-03 and ORG-04 are placeholders until real names are given.
- Identity from Office 365 connectors: email and display name come from the Office 365 user connector. Roles come from a Roles list keyed by email, replacing Acces_Matrix and the Master_Employee lookup.
- Design streamlining: from 30 screens to about 10, one screen per job. Master data uses one list-and-edit screen per table, removing the -New twins. Stock opname uses one screen for both available and in-use.
- Architecture streamlining: access checks once (gblRoles), asset scope by function instead of hardcoded IDs, shared formulas in app-level named formulas, one literal per status and access value, and flows that take an Entity parameter. Dead flows are removed.

Migration phases
1. Data: add the Entity column, backfill existing rows, create Roles from Acces_Matrix.
2. Identity: switch access checks to email and Roles.
3. Entity picker: add gblEntity and filter every query on it.
4. Shared components and theme, built before any screen uses them.
5. Screens: rebuild one job at a time, retiring old screens after testing.
6. Flows: add the Entity parameter and remove dead flows.
7. Clean-up: remove unused lists and screens.
